### D-2. 阶段 A/B/UI/DOM 验收读数

> 阶段 B 验收（FSRS-6）:调度为纯函数、单次 review 亚毫秒（与题量无关）；个性化训练 21 权重数值梯度（中心差分 ×2 + 迭代内 loss）实测中位 **3.89 s / 3200 样本**，仍在 Worker 30 s 超时内，留出集改善 2.84%。
> **阶段 B 增量重训（P1）验收**：以全量训练结果为热启动起点、迭代减半（150→60），同一 bench 内 **3893.58 ms → 1548.56 ms（2.51× 提速）**，留出集改善 **2.89%**（≥ 全量 2.84%），门控基线仍为官方默认（口径不放宽）。**注意计时受机器负载影响波动**：另一轮同机实测为 3960.86 ms → 3099.41 ms（1.28×）——结构收益恒定（梯度评估次数 150→60），墙钟比值随负载而变。
> **阶段 B 公式子集（P2）验收**：`\frac`/`\sqrt` 混排渲染中位 **0.01 ms**（零依赖 CSS 排版）。**真实浏览器校验**（`node scripts/serve.mjs` + 自动化浏览器，临时页加载真实 `css/style.css` + `js/utils/rich-text.js`）：computed style 证实 `.rt-frac` 为 `inline-flex; flex-direction: column`、分母 `border-top-width: 1px`、分子/分母边界框上下分层；`.rt-sqrt::before` content 为 `√`、`.rt-radicand` `border-top-width: 1px`、`\sqrt[3]` 的 `.rt-index` 文本为 `3`；根号内嵌分式与 `sup` 节点均在位。截图因浏览器标签被节流而不可用（如实记录）。

> 阶段 A 规模验收：3000 题单库下，**按需单页冷读 0.24 ms** 与库规模解耦（全量冷读 3.70 ms，约 15×）；**单题 update 0.38 ms** 与库规模无关（全量重写 38.49 ms，约 101×）。
> **UI 级按需加载验收（阶段 A）**：改造前每次 `render` 均整库全量冷读（3000 题 3.70 ms）→ 改造后**装载缓存命中 0.00 ms、答题交互视图装载 0.00 ms**；装载仅在题库或题目变动（写修订号变化）后首次付出一次（3.57 ms）。首屏/答题 HTML 构建 0.02/0.04 ms 且**与库规模无关**（首页 HTML 2414/2411 字符、答题区 7248 字符，随本场题数而非库规模）。
> **DOM 增量更新验收（阶段 A）**：`#view` 改走 `QB.DomPatch` 区域对账（列表 + 答题区，含**答题卡格级增量**）。**列表侧**——错题本移除一条仅重建 1/22 区域（占其 HTML 字节 0.9%），其余 20 个区域保留原 DOM 节点（保住焦点/滚动）。**答题区**——勾选选项时顶层仅重建 3/5 区域（占字节 15.6%）；答题卡由「整卡单区域」细化为 `frame` + `sub`：帧跨作答逐字节不变（整张 `<details>` 不重建，展开态不丢），仅按 key 就地替换变化的 **3/52** 子节点（计数 + 受影响格，占整卡 HTML 字节 2.0%）。相较细化前（整卡占答题区字节约 95.6%），答题热路径重建量 **由 95.6% 降至 15.6%**。**浏览器实机验证**：折叠答题卡后作答，卡片保持折叠（证明 `<details>` 未被重建）；作答使选项态/提交按钮/计数/当前格状态同步更新，控制台无报错。
> `insertMany` 落库耗时以 v3（64 位）contentHash 语义哈希重算为主（约 11.32 ms / 541 题），**与分片写入无关**——分片写入（`writeAll` 3 片 + 清单整体）远低于旧单键写。历史记录的 1.65–1.78 ms 系 v1 裸 hash 时代口径（v2 哈希上线后即升至 4.97–5.38 ms，见 `CHANGELOG.internal.md`），非本批退化；v3 的 BigInt 64 位哈希比 v2 的 32 位慢（单次约 2 倍），仍在门禁（≤30 ms）内。

> **作用域键视图 `keysScoped`（C 步骤1，2026-11-08，50k/IDB 档，同机 `--expose-gc`，5 采样，观测行 · 未进门禁）**
> - 实测（两次同机复跑）：中位 **8.03 / 10.66 ms**（min 7.24–7.55 / max 9.97–11.81），返回「全局 + 目标库」键 **50,361 个**（与同轮 `keys()` 逻辑键数一致）；两轮差异属机器负载波动，如实并列。
> - 实现：复用 `keys()` 同一份物化缓存（`_keysRawCached` → `_keysCache`/`_buildKeys`），按 `bankOfKey` 前缀过滤，**不建库索引、不增加常驻内存**；成本随键总数线性（O(键数)），首次调用若恰逢缓存失效会额外付一次 `keys()` 重建（本次测量为命中路径）。
> - 依赖：`_keysCache`（物化结果）与 `_chunkStates`（复习块展开为逻辑键）；`_pending`（未落盘写入）由 `_buildKeys` 一并合并，所以作用域视图不会漏掉防抖中的新键。
> - **未进门禁**：该行只观测、不设阈值（跨机器过滤成本波动不稳定）；当时文档记「门禁数仍为 66 项」，其中含三档 IDB 写入的重复计数，实际互不重复的门禁是 **63 项**（见文首「门禁条数口径」）。提案估算 3–4 ms 与实测 8.03–10.66 ms 的差异如实记录，未据此调任何阈值。

### D-9. 评分路径端到端耗时（一次作答 → 结果可读，真实浏览器 IndexedDB，2026-11-13）

**口径**：从评分调用进入（`WrongBook.add` 错题入队 + `SRSStore.grade`）到错题条目、`last`、revlog 在**真实 Chromium IndexedDB** 提交后可被新事务直读确认为止。只作数据记录，不新增门禁、不改任何阈值。

**环境**：Node v26.13.0 驱动 Microsoft Edge 142.0.3595.53（headless，CDP），Windows 10.0.19045 / i5-11400 12 核 / 32,534 MB（测量时可用 20,561 MB）。应用跑本地 HTTP 静态服务，每个进程使用全新临时 profile，IndexedDB 落盘在该 profile 内（**不是 `idb-memory` 替身**），启动后 `QB.Storage.mode === 'idb'`。

**方法**：
1. 新建 20 题单选库，同路径预热 60 次。
2. 每样本：`t0` → `WrongBook.add` → `SRSStore.grade(...)`（内部 `await flush()` 确认 IDB 事务）→ `t1`（写入确认）；随后 `QB.Store.get` 直读底层 IDB 的 review chunk / wrong / `revlogMeta` + 尾段，三项校验（`last` 与 `grade` 返回值相等、错题条目存在、revlog 记录存在）通过后记 `t2`（可读端到端）。
3. 5 轮 × 200 样本/进程 × 3 个独立浏览器进程 = **3,000 样本**，**3000/3000 校验通过**（无一次读到旧值）。

| 进程 | 样本 | 写入确认 `grade` P50 / P95 / min | 可读端到端 P50 / P95 / min–max | 轮中位数（5 轮） |
|---|---|---|---|---|
| 1 | 1000 | 1.0 / 1.8 / 0.7 | 1.6 / 2.7 / 1.1–15.9 | 1.6 / 1.6 / 1.5 / 1.5 / 1.5 |
| 2 | 1000 | 1.0 / 1.8 / 0.6 | 1.5 / 2.7 / 1.1–14.6 | 1.5 / 1.6 / 1.5 / 1.6 / 1.5 |
| 3 | 1000 | 1.0 / 1.8 / 0.7 | 1.5 / 2.7 / 1.1–14.8 | 1.5 / 1.6 / 1.5 / 1.6 / 1.5 |
| **合计/合并** | **3000** | **1.0 / 1.8 / 0.6** | **1.5 / 2.7 / 1.1–15.9** | 15 轮全部 1.5–1.6（极差 1.07×） |

单位 ms。`grade` 列为写入提交确认成本；可读列比它多约 **0.5 ms**，即三次直读确认的开销（3 个 `Store.get`，含一次 meta + 尾段读取）。

**负向对照（同脚本临时注入，不进门禁）**：在测量区间内忙等 +1 ms → 可读 P50 **3.0** / 写入 P50 **2.2**；+0.3 ms → 可读 **2.1** / 写入 **1.5**（各 1 进程 × 1000 样本）。两次注入都清晰越出基线 1.5 ms，说明该口径对 **0.3 ms 量级** 的路径变慢有分辨力。

**已知边界（如实）**：
- 计时分辨率：Chromium `performance.now()` 约 0.1 ms 台阶；P50 由 1000 样本合成，分辨率优于单样本，但**不可分辨 <0.1 ms** 的差异。
- 「可读」= 新事务已能读到（事务已提交），**不等于**操作系统刷盘完成或断电持久性。
- 数据规模：20 题新库、错题 ≤20 条、revlog 尾段 ≤200 条、review chunk 很小。该路径只重写所在 chunk / 错题数组 / 尾段，但错题数组随错题总数线性增长；**数千条错题或多题库下未测**，绝对耗时可能更高。
- 负载：Windows 无 loadavg，仅记录可用内存；3 个独立进程 P50 稳定在 1.5–1.6 ms，但这是**空闲态同机参考值**，重负载下 IDB 提交调度会变慢。可分辨约 **≥0.3 ms（≈20%）** 的变化；更小的变化需增大样本或改用 CPU 计时探针。
- 与 D-6 不可直接相减：D-6 的 0.03–0.68 ms 是 Node 内存 IDB 的实现级写入，本项是浏览器真实 IDB 的完整用户路径（错题 + 提交 + 直读确认）。

# 性能打点与门禁（BENCH）

> **这份文件是什么**：`DEVELOPMENT.md` 原 §3。
> **为什么单独成文**：它是读数档案 + 红线，随每次复测追加，与"怎么装环境"无关。
> **读数口径**：本文里的数字由 `scripts/docs-check.mjs` 复算校验（它同时读 README / DEVELOPMENT / 本文）。

```bash
npm run bench                                # = node --expose-gc scripts/bench.mjs --assert（默认即门禁，63 项）
npm run bench:observe                        # 只观测不判定（记录轮次/容量读数用）
node --expose-gc scripts/bench.mjs --assert   # 性能门禁：63 项阈值 + heapUsed ≤40MB，超限退出码 1（CI 在 Node24/Asia-Shanghai 跑）
node --expose-gc scripts/bench.mjs --scale=50000   # 可选规模测量（LocalStorage 估算字节/迁移耗时/heap；不进门禁，口径见 DATABASE.md §9）
```

> **默认即门禁（C005）**：`npm run bench` 曾只观测、不判定，且 `npm run verify` 不含 bench——
> 用 `QF_BENCH_INJECT_SLOW=0.1` 注入 10% 慢化后，旧 `npm run bench` 仍 exit 0（仅 `--assert` 才退 1）。
> 现在 `bench` 直接带 `--assert`，`verify` 也包含它；只想看读数用 `bench:observe`。

> **门禁条数口径（2026-11-12 更正：63 项，不是 66 项）**：`--assert` 实际执行 **63** 条互不重复的判定，
> 每条打印一行 `  ✓ ` / `  ✗ `。历史文档写的 66 项是**重复计数**——`IDB 单次评分写入（5000/20000/50000）`
> 三档同时被 `BUDGETS` 表与独立判定块各判一次（`28f88e8` 起），同一断言打印两行；`4d4ec51` 删掉
> `BUDGETS` 里的重复三条后实跑降到 63 行，但基线与文档没跟着改。现在做三方对账：
> `bench.mjs` 的 `const GATE_TOTAL`（声明）＝ 实跑 ✓/✗ 行数 ＝ `docs-baseline.json` 的 `gateCount`
> ＝ 本文与 README/DEVELOPMENT 的「N 项阈值」，任一方不一致 `bench` 或 `docs-check` 立即红。
> **目前不存在"声明总数 ≠ 本机执行数"**（63 项全部执行，无跳过、无条件分支）；若将来加入按 Node 版本或
> 平台跳过的门禁，必须在此写清「声明 N 项、本机执行 M 项、K 项因 X 跳过」，`GATE_TOTAL` 只表示声明总数。

> **`--expose-gc` 是门禁前提**：不带该参数时 `heapUsed` 增量含未回收垃圾，`heapUsed ≤ 40MB` 门禁不可信——
> 同一基线 `740512e` 的独立 worktree 实测 **91.07MB**（同样超限），并非代码回归。CI（`.github/workflows/test.yml`）
> 与 `scripts/docs-check.mjs` 均以 `--expose-gc` 运行。

> **bench 红必须带上取证**：`--assert` 失败时脚本自动把失败项、完整门禁清单（✓/✗ 与实测值/阈值原文）、
> Node/OS/CPU/内存与注入开关快照写到 `.analysis/bench-failures/<ISO>-bench-failure.json`（`.analysis/`
> 已在 `.gitignore`）；绿时不产生任何文件。报告性能红灯时**须附上该文件内容**，否则视为无证据——
> 曾出现过「bench 整体 exit 1 但没记录到哪一项红」，此后不再接受这种报告。

> **作用域键视图 `keysScoped`（C 步骤1，2026-11-08，50k/IDB 档，同机 `--expose-gc`，5 采样，观测行 · 未进门禁）**
> - 实测（两次同机复跑）：中位 **8.03 / 10.66 ms**（min 7.24–7.55 / max 9.97–11.81），返回「全局 + 目标库」键 **50,361 个**（与同轮 `keys()` 逻辑键数一致）；两轮差异属机器负载波动，如实并列。
> - 实现：复用 `keys()` 同一份物化缓存（`_keysRawCached` → `_keysCache`/`_buildKeys`），按 `bankOfKey` 前缀过滤，**不建库索引、不增加常驻内存**；成本随键总数线性（O(键数)），首次调用若恰逢缓存失效会额外付一次 `keys()` 重建（本次测量为命中路径）。
> - 依赖：`_keysCache`（物化结果）与 `_chunkStates`（复习块展开为逻辑键）；`_pending`（未落盘写入）由 `_buildKeys` 一并合并，所以作用域视图不会漏掉防抖中的新键。
> - **未进门禁**：该行只观测、不设阈值（跨机器过滤成本波动不稳定）；当时文档记「门禁数仍为 66 项」，其中含三档 IDB 写入的重复计数，实际互不重复的门禁是 **63 项**（见文首「门禁条数口径」）。提案估算 3–4 ms 与实测 8.03–10.66 ms 的差异如实记录，未据此调任何阈值。

> - 红/绿：红跑 `通过: 88，失败: 3`（再次渲染期望 1 实得 2 / 日志变更后期望 2 实得 3 / 离开再进入期望 2 实得 4）；绿跑 **91 通过 / 0 失败**，exit 0。原始输出：`.analysis/architecture-audit/stage3-red-p6.txt` 与 `stage3-green-p6.txt`。

> - 未实机验证：真实浏览器切页时的 long-task/帧时间；本项只度量 Node 侧扫描成本与调用次数。

> 红线：不允许凭感觉声称性能。改动后必须重跑 bench，把新数据写进提交信息与 `CHANGELOG.internal.md`；内存/P95 不达标继续改，不强行提交。

### 3-B. SRS 相对门禁（同轮标定比值）

**为什么改掉绝对毫秒阈值**
- 旧规则：`SRSStore.grade / gradeMany` 的 9 轮全样本 p50 ≤ **历史某次运行**的基线 ×1.05（0.0810 / 0.2604 ms）。
- 2026-11-03 同机复测：HEAD **0.0902 / 0.2787 ms**；同机跑旧代码 `e772e60` 为 **0.0882 / 0.2784 ms**，同样超限 → 机器漂移，不是本轮代码回退（本轮改动不进入 SRS 热路径）。
- 该口径有两个结构性问题：机器变慢 → **误报**；机器变快 → 阈值被动变宽 → **漏报真实回退**。因此不改阈值，改测量方法。

**方法**
- 每轮（共 21 轮）在被测样本批次**前后各跑一批标定工作**；标定工作与存储提交（`local-adapter` patch）同构：状态对象合并、200 条日志段拷贝、状态/尾段/首段/元数据 `JSON.stringify`、Map 缓存查表。标定只用标准 JS 常量与基元，不调用业务模块。
- 单轮判定量 `ratio = 本轮被测中位数 / 标定单位耗时`（前后两批取均值）；**门禁判定量取 21 轮比值的 p25**（不是轮中位数的中位数，理由见下）。
- 标定窗口与样本批次**同量级**：grade 每轮 5000 单位（≈200 ms）、gradeMany 每轮 2000 单位（≈80 ms）（`unitsPerSample` 5 / 10）。原标定仅 3–4 ms，与 80–200 ms 的样本批次处在不同 CPU 频率斜坡上，负载一起来两侧不同步。
- 门禁：`ratio(p25) ≤ 基线 × 容差`，**两项各自一个容差**（`node.<ver>.tolerance`），基线按 **Node 大版本** 存放于 `scripts/bench-baseline.json`。遇到未登记的大版本 **fail-closed**（直接判失败并提示「测量后补基线」），禁止拿别的引擎数字顶替。

**为什么把判定量从「轮中位数的中位数」改成「21 轮比值的 p25」（2026-11-12）**
- 旧口径（11 轮、标定 3–4 ms、判定量 = 11 轮比值中位数）连跑 20 次：grade **4.67–5.51**（p50 4.99），gradeMany **8.42–11.79**（p50 9.43，极差 **1.40×**），20 次里 **9 次红**。逐轮数据呈双峰（如 gradeMany 11.35/8.58/11.60/8.52…）：负载只会让个别轮变慢，中位数被周期性慢轮整体抬高，阈值 5.29 / 9.48 正好压在分布中部——这是当天反复误红的直接原因。
- 改法：轮数 11→21、标定窗口拉到与样本批次同量级、判定量取 **p25**。p25 取的是「这台机器上该路径的内在成本」，少数慢轮不再拖动判定值；同口径连跑 20 次，两项极差都收窄到 **1.10×**（见下表）。

**容差推导（两项分开，不共用数字）**
- 规则：`容差 = max / p50 × 1.03（采样余量）`，再向上取两位小数。取 max 而不是 p99 是因为本次 20 次里 p95 与 p99 同为次大值（样本少时 p99 不供额外信息），max 已覆盖观测上界，再乘 3% 覆盖「下次运行略慢于本次 20 次的极值」。

- `gradeMany`（Node 26）：8.67 / 8.40 = **1.0321** → ×1.03 = **1.0631** → 取 **1.07**，阈值 8.40×1.07 = **8.99**。
- `grade`（Node 24）：2.55 / 2.43 = **1.0494** → ×1.03 = **1.0809** → 取 **1.09**，阈值 **2.65**。
- `gradeMany`（Node 24）：4.66 / 4.54 = **1.0264** → ×1.03 = **1.0572** → 取 **1.06**，阈值 **4.81**。

- `keysBuild` 已于 2026-11-12 退出比值体系（探针日间漂移 30%，见 **3-B-1**），顶层默认 **1.06** 仅作为 SRS 未单列指标时的回退值。

**这套容差能抓住多大的回归**
- **≥20% 必然抓得住**：按本次最快观测态（grade 4.44、gradeMany 7.86）估算，+20% 后为 **5.33 / 9.43**，分别高于 5.07 / 8.99。
- **10% 取决于运行态**：按 p50 态（4.69 / 8.40）+10% 得 **5.16 / 9.24**，均越线；按最快态 +10% 得 **4.88 / 8.65**，抓不到。即 10% 级回退是否报警依赖当次机器状态，**保证可抓的下限是 20%**；若要求 10% 必抓，容差需压到约 1.04，会把 20 次观测里的 max 变成常态误红，故不采用（如实记录该折中）。

**Node 26 归因（2026-11-11，先归因后调基线）**
- 同一份代码、同一台机器：Node 24 比值 `2.58 / 4.78`（p50 0.21 / 0.37 ms，标定 78.6 / 77.5 µs）；Node 26 比值 `4.99 / 8.94`（p50 0.14 / 0.24 ms，标定 27.5 / 27.0 µs）。**该组数字是旧判定量（轮中位数口径）**，2026-11-12 改为 p25 + 同量级标定窗口后，Node 26 基线变为 **4.69 / 8.40**（见上表），Node 24 变为 **2.43 / 4.54**——两者不可混用。
- 绝对值在 Node 26 上**更快**（grade 0.21→0.14 ms），但标定工作被 V8 优化得更狠（78.6→27.5 µs，约 2.9×），比值因此被推高 → **引擎/标定差异，不是代码回退**。
- 结论：按主版本分量基线，而不是把全局基线抬到 4.99；同时把 Node 26 加入 CI bench 腿，让两套基线都持续被测。
- 证据留档：`work/bench-node24.log`、`work/bench-node26.log`（三轮 Node 26 比值 5.19 / 4.94 / 4.99，gradeMany 8.94 / 8.86 / 8.94）。

**为什么它能区分「机器漂移」与「代码回退」**
- CPU 频率/负载/GC 相位/JIT 状态会**同时**作用于被测路径与标定路径，在比值中同向抵消。
- 真实回退只发生在被测路径（分子），标定路径不变 → 比值单向上升；标定不引用业务实现，业务回退不会把标定值一起抬高。
- 容差由实测分布推导（1.07 / 1.08，见上），覆盖 20 次观测上界再留 3% 余量：按 p50 态估算仍能抓住 10% 级回退，按保证下限（最快态）能抓住 20%；再放宽会让 10–20% 级回退整体淹进噪声。

**测量前置条件（绝对毫秒不再可与旧口径比较）**
- **必须 `--expose-gc`**：每轮前 `global.gc()` 两次，消除堆相位差；无该参数时比值仍输出，但波动明显更大。
- 测量前把全局 revlog 灌到 `REVLOG_MAX`（20000），固定「尾段写 + 满段 FIFO 裁剪」稳态；否则测量窗口跨越 cap，p50 取决于越界轮次，不可复现。
- 标定拆 10 个小批取中位数，避免单批 GC 抬高单位耗时；每轮标定工作量已拉到与样本批次同量级（见「方法」），改动该量即作废两套基线。
- 因 revlog 预灌，新口径 p50（grade ≈0.16 ms、gradeMany ≈0.29 ms）**高于**旧口径（0.08 / 0.25 ms），二者不可直接比较；判定只看比值。

**适用边界（未验证项如实列出）**
- 已验证：Windows + Node v24.22.2（8 次）与 v26.13.0（20 次）、同机同负载量级、21 轮×1000 / 21 轮×200。
- **未验证**：跨 CPU 架构（x86/ARM）、容器限核/CI 共享核、swap 与磁盘 I/O 抖动、极端后台负载。接入新环境时应先跑 3 次记录比值，再决定是否新增该环境的基线（不是放宽容差）。
- 若某机器上「标定工作」与「业务 patch」对硬件特性的敏感度差异超过容差（7–9%），比值基线会整体平移，仍可能误报/漏报；这是相对法的固有边界。
- 覆盖不到：首次冷调用 JIT 编译（取中位数已排除预热阶段）、真实磁盘 I/O（bench 用内存适配器，不落盘）、GC 长暂停（p25 削弱但非消除）。

**负向验证（2026-11-12，Node 26.13.0，干净 worktree @ `1c97758` + 本轮脚本）**
```bash
QF_BENCH_INJECT_SLOW=0.2 node --expose-gc scripts/bench.mjs --assert   # 两项均 ✗、退出码 1
QF_BENCH_INJECT_SLOW=0.1 node --expose-gc scripts/bench.mjs --assert   # 两项均 ✗、退出码 1（本次运行态偏慢）
node --expose-gc scripts/bench.mjs --assert                            # 撤掉注入：两项均 ✓、退出码 0
```
- 注入只在 `scripts/` 侧：每个被测样本前插入 hrtime 截止时间忙等，时长 = 比例 × 该路径实测中位数；**不修改** `srs-store.js` / `fsrs.js` / `local-adapter.js`。
- 实测：+20% → grade p25 **5.93 > 5.07 ✗**、gradeMany p25 **10.04 > 8.99 ✗**（exit 1）；+10% → grade **5.12 > 5.07 ✗**、gradeMany **9.36 > 8.99 ✗**（exit 1，该次运行 p50 比值 5.54 / 10.25，属偏慢运行态）；无注入 → **4.33 / 7.88**（✓，exit 0）。
- 如实说明：10% 注入口径下两项越线幅度很薄（5.12 vs 5.07），在最快运行态（4.44 / 7.86）按公式估算抓不到；**保证可抓的下限是 20%**，与上节估算一致。
- 注意忙等会轻微拉高 CPU 频率、使随后样本略快，从而**低估**注入幅度；因此不能用注入结果「证明」门禁更灵敏，只能证明「该幅度在本容差下会被判红」。

### 3-B-1. keys() 视图门禁：首次构建 10 轮最小样本 + 命中自比值（2026-11-12 定稿）

**旧口径为什么失效**
- 旧规则：`keys() 首次构建（50000 · IDB）` 对「50000 次纯内存字符串物化」探针的同轮比值 ≤ 基线 × 1.06（Node 24 基线 1.38、Node 26 1.41）。
- 反证（2026-11-12）：`js/utils/storage.js` 自基线提交 `866f784` 到 HEAD **零改动**（`git diff 866f784..HEAD -- js/utils/storage.js` 为空），但
  - Node 24.22.2 连跑 6 次比值 **1.43 / 1.47 / 1.48 / 1.49 / 1.50 / 1.52**（中位 **1.485**），**6 次全部 > 阈值 1.46**；
  - 同一天 Node 26.13.0 的比值跌到 **1.07–1.16**（探针中位从 21.6 ms 漂到 26–28 ms），远低于基线 1.41。
- 归因：探针自身日间漂移 **30%**（Node 24 13–20 ms、Node 26 21–28 ms，同一天内也摆 1.3×），比值不是稳定量。这正是 CI `logic-tests (24, Asia/Shanghai)` 的 bench 步长期红、Node 26 偶发红，而本地六格全绿同源码的原因——**测量口径问题，不是业务回退**。

**新口径：首次构建 10 轮最小样本（绝对判据）+ 命中自比值**
- `keys() 首次构建（50000 · IDB）`：10 轮 × 20 样本，每轮前强制 GC，判定量 = **全局最小样本**，上限 = Node 大版本基线 × **1.35**：Node 24 基线 **15.95 → 21.53 ms**，Node 26 基线 **21.70 → 29.30 ms**；未知 Node 大版本 **fail-closed**。
- 为什么用最小值：负载/GC 只会让个别样本或某一轮变慢，**不会把最小值拉低**，所以最小值是稳定的绝对估计；中位数会被 GC 长尾抬高（同机 Node 24 单次运行中位 19.7–26.5 ms，摆 **34%**），40 ms 量级的中位数门禁挡不住正常漂移。而「命中 ≤ 首次/10」是自比值，构建整体变慢时按比例放宽，**结构上抓不到构建退化**，故只作附加判据。
- 附加：`keys() 写入已存在键后`（3 轮 × 20 样本）的**中位数** ≤ `max(首次构建中位数 / 10, 1 ms)`，抓「任何写入即失效 → 每次 `keys()` 重建」（自比值≈1）。
- 两版本分基：最小值口径下 Node 24 **15.95 ms**、Node 26 **21.70 ms**，差 **1.36×**，超出 1.35 容差能吸收的范围；同一基线会让一版长期误红或放水。

**10 轮最小值原始数值（2026-11-12，干净树，TZ 无关）**

| 版本 | 10 轮最小值（ms） | 全局最小 | 轮间极差 | 基线×1.35 = 阈值 |
|---|---|---|---|---|
| Node 24.22.2 | 16.22 / 17.92 / 16.88 / 15.95 / 16.50 / 16.13 / 17.73 / 16.40 / 17.43 / 16.59 | **15.95** | 1.12×（12%） | **21.53 ms** |
| Node 26.13.0 | 22.40 / 21.70 / 23.57 / 22.08 / 23.87 / 23.00 / 22.61 / 23.09 / 23.88 / 24.06 | **21.70** | 1.11×（11%） | **29.30 ms** |

- 1.35 的来源：覆盖实测轮间极差（11–12%）与日间漂移，同时保留抓住 1.5× 退化的余量——Node 24 **1.5× = 23.93 > 21.53**，Node 26 **1.5× = 32.55 > 29.30**。Node 24 另一次无注入复跑最小 **14.83 ms**，说明基线取在最快态 7% 以内（偏保守一侧）。

**抓得住 / 抓不住**
- **抓**：首次构建 ≥1.5× 退化（按实测基线）；「任何写入都让视图失效」（自比值≈1）；未知 Node 大版本（fail-closed）。
- **抓不住**：<1.35× 的退化（吸收日间漂移的代价）；整机变快 >12% 时，同一段代码的 1.5× 可能落到阈值下——此时绝对值仍在 20 ms 量级，用户可感知预算未被突破。
- **误红而非放水**：整机降频/限核使最小值升 >35% 时正常代码也会红，这是刻意保留的信号（先查环境，不放宽基线）。真实磁盘 I/O、冷 JIT 不在覆盖范围（内存 IDB 替身）。

**负向验证（只让首次构建变慢）**
```bash
QF_BENCH_INJECT_KEYS_BUILD_SLOW=1.5 node --expose-gc scripts/bench.mjs --assert   # ✗、退出码 1
QF_BENCH_INJECT_KEYS_BUILD_SLOW=2   node --expose-gc scripts/bench.mjs --assert   # ✗、退出码 1
node --expose-gc scripts/bench.mjs --assert                                       # 撤掉 → ✓、退出码 0
```
- 注入只在 scripts 侧：先跑 20 样本 pilot（不计入判定），每个首次构建样本前置忙等 = pilot 最小值 × (倍数−1)；不改 `storage.js`。
- Node 26：+12.34 ms/样本（1.5×）→ 最小 **35.63 > 29.30 ✗**；×2（+22.69）→ **46.48 > 29.30 ✗**。
- Node 24：+7.56 ms/样本（1.5×）→ 最小 **22.76 > 21.53 ✗**（余量 5.7%，仍判红）；无注入复跑 **14.83 ≤ 21.53**、写后 **0.09 ms**，63/63 ✓。
- 忙等会轻微抬高 CPU 频率使随后样本略快，故注入结果只证明「该幅度会被判红」，不证明门禁更灵敏。

**写入即失效（附加判据负向验证）**
```bash

```
- Node 26：首次 26.84 / 写后 **27.13 ms** > max(2.68, 1) → ✗；撤掉后 27.61 / **0.12** → ✓。Node 24 写后 **0.08 ms** → ✓（无注入）。注入只清 `_keysCache`，不改业务代码。

**边界**
- 10 轮 × 20 样本、每轮前强制 GC 是口径的一部分；改动须重新实测并同步本节与 `scripts/bench-baseline.json`。换机器应重新建基线，不沿用本表数字。
- 最小值对「整机持续降频/限核」不免疫；本机正常态 15–22 ms，距阈值 21.53 / 29.30 ms 有 1.35× 余量。

### 3-B-2. IDB 单次评分写入：为什么不做同轮标定比值（改用最小样本）

**结论**：这一条**不做**比值化。探针测的是 CPU/内存吞吐，而写入抖动来自事务提交（双微任务完成）与 GC/事件循环调度，纯内存探针在结构上代表不了它；硬套只会把「随负载翻转」换成「随探针抖动翻转」。判定改为「5 轮 × 20 样本的全局最小样本 ≤ 1 ms」，上限仍是 **1 ms（未放宽）**。

**比值实测为何不成立（2026-11-12，Node 26.13.0，同一 HEAD）**
- 探针按 3-B-1 的思路构造：独立 `createMemoryIDB` 实例，每轮写 1 个状态键 + 200 条日志段，走完整 `put` 与事务完成（`recordBytes` 两次 `JSON.stringify`），不调用业务模块。
- 三轮比值：5000 档 **1.59 / 1.71 / 1.33**，20000 档 **8.26 / 7.05 / 6.92**，50000 档 **9.97 / 9.74 / 8.00**；轮间极差 **19–29%**，是 6% 容差的 3–5 倍。
- 探针自身耗时只有 0.06–0.10 ms（绝对抖动即 ±67%），与被测值同量级——分母的噪声不比分子小。
- 把探针加大到 30 样本 / 5 轮仍不稳（5000 / 20000 / 50000 = **1.33 / 6.92 / 8.00**）。
- 根因：`keys()` 的抖动是「50k 字符串物化」的 CPU 成本，同性质探针可以抵消（3-B-1 实测比值只摆 4%）；IDB 写入的抖动是事务排队与 GC 相位，探针越接近纯 CPU，越抵消不了。故判定**不适合比值化**，按任务约定不改实现为比值。

**替代判定：最小样本**
- 每档 5 轮 × 20 样本（共 100 样本），判定值取**全局最小样本**；每轮前强制 GC（与 3-B-1 同一复现性前提）。
- 为什么用最小值：写入是重尾分布（单样本 max 7.6–84.4 ms，来自 GC 长暂停与事务排队），1 ms 预算只可能被尾部击中；最小值代表「这台机器此刻单次写入的成本下限」，对突发负载尖峰免疫，同时不会掩盖真实回退（代码回退会抬高整个分布，含最小值）。
- 与比值法的区别如实写明：最小值对**整机持续降频/限核**仍会上升，这是刻意保留的信号（属机器容量问题，应查环境而非放宽 1 ms）；比值法能抵消这种平移，但在本条上换不来稳定性。

**实测（最终代码，Node 26.13.0；两次独立进程 + 一次高负载轮）**

| 档位 | 轮中位数（5 轮） | 中位数 | 最小样本 | 判定（min ≤ 1 ms） |
|---|---|---|---|---|
| 5000 | 0.367 / 0.088 / 0.199 / 0.126 / 0.256 | 0.20 | 0.08 | ✓ |
| 20000 | 0.476 / 0.561 / 0.510 / 0.479 / 0.512 | 0.51 | 0.33 | ✓ |
| 50000 | 0.660 / 0.677 / 0.684 / 0.806 / **1.228** | 0.68 | **0.58** | ✓ |

第二次（同树连跑，退出码 0）：50000 轮中位 **0.683 / 1.048 / 0.709 / 0.675 / 1.492**、中位 0.71、最小样本 **0.61 → ✓**；第三次（高负载轮）：50000 轮中位 **0.616 / 0.948 / 0.760 / 1.008 / 1.101**、中位 0.95、最小样本 **0.51 → ✓**。三档最小样本三次分别为 **0.08 / 0.08 / 0.08**、**0.33–0.42**、**0.51–0.61 ms**。

**判定不随负载翻转的证据**：三次实测里 50000 的轮中位数最高 **1.492 ms**、中位数最高 **0.95 ms**——**旧的中位数门禁在第二次与第三次都会变红**（1.492 / 1.048 / 1.008 均 > 1 ms），而代码一行未改；最小样本始终 0.51–0.61 ms ✓。

**负向注入（只让这一条写入路径变慢）**
```bash
QF_BENCH_INJECT_IDB_WRITE_SLOW=10 node --expose-gc scripts/bench.mjs --assert   # 三档全 ✗、退出码 1
node --expose-gc scripts/bench.mjs --assert                                     # 撤掉注入：三档全 ✓、退出码 0
```
- 注入只在 scripts 侧：先跑一轮 20 样本标定（**不计入判定**），之后每个被测样本前置 hrtime 忙等 = 标定中位数 × 倍率；不改业务代码。
- 10× 注入：+4.49 / +4.45 / +6.83 ms/样本 → 最小样本 **4.71 / 4.67 / 7.22 ms**，三档全 ✗，`EXIT=1`。
- 2× 注入：+0.72 / +0.94 / +1.24 ms/样本 → 最小 **0.81 / 1.09 / 1.56 ms**——20000 / 50000 ✗，5000 仍 ✓（该档标定中位仅约 0.15 ms，+0.72 ms 尚未越过 1 ms），整体 `EXIT=1`。
- 两轮注入中其余门禁（SRS 两项、`keys()` 首次构建、迁移、heap）全部维持 ✓：只有目标路径变慢，门禁没变钝。

**边界**
- 最小样本对「整机持续降频/限核」不免疫（见上）；本机 50k 档实测地板 0.51–0.61 ms，距 1 ms 有 1.6–2 倍余量。
- 5 轮 × 20 样本、每轮前强制 GC 是口径的一部分，改动需重新实测并更新本节数字。
- 未覆盖：真实浏览器 IndexedDB 的磁盘事务语义（bench 用内存替身，口径声明见 `scripts/lib/idb-memory.mjs`）。

### 3-C. 哪些绝对阈值取三轮中位数、哪些保持单轮（取舍）

门禁的判定量都是中位数，但**单轮取样**在重尾分布上不稳：同一个 HEAD 连跑两次，`IDB 单次评分写入（50000）` 得到 1.13 ms 与 0.60 ms（阈值 1 ms），单样本 max 达 110 ms（GC 长尾）。因此按下面的分工处理，阈值一个都没动（`IDB 单次评分写入` 后来改为最小样本判定，见 **3-B-2**，本节其余分工不变）。

**取三轮**（`stableTimed(fn, n, 3)`；`per-hash` 判定取**全局最小样本**）：

- `per-hash 单次评分本地写`（20000 档，20 样本 × 3 轮；2026-11-12 起判定量从轮中位数改为最小样本：中位数被 GC 长尾污染，同机 Node 24 实测 0.18→0.38 ms 摆动 2.1×，阈值与相对判据不变）
- `keys() 写入已存在键后`（50000，20 样本 × 3 轮，判定取轮中位数；绝对耗时约 0.08–0.12 ms）

这些被测操作在 0.02–0.6 ms 量级，阈值是 1 ms 的绝对值，中位数离阈值近，长尾足以翻盘；三轮的额外成本可以忽略。

> `keys() 首次构建（50000）` 改为 **10 轮 × 20 样本的最小样本绝对门禁**（Node 大版本分基，见 **3-B-1**）；「写入已存在键后 vs 首次构建」的同进程自比值作附加判据。`Storage.keys()` 本身未改动。

**保持单轮**（`timed(fn, n)`，默认 10 或 5 样本）：

- `insertMany 落库`、`规模库 insertMany overwrite 全量重写`
- `schema v5 迁移`（1000 / 3000 / 20000）
- `FSRS 优化器 computeTrain`（4000 条 / 150 迭代，单次约 5.5 s）

**取舍依据（2026-11-11 实测，同一 HEAD 连跑 10 次独立进程，Node 26.13）**：

| 打点项 | 阈值 | 10 次中位数范围 | p50 | 最差中位数/阈值 | 单样本峰值/阈值 |
|---|---|---|---|---|---|
| `insertMany 落库` | 30 ms | 7.81–10.34 | 8.95 | 34.5% | 43.2% |
| `规模库 insertMany overwrite` | 80 ms | 30.13–35.89 | 33.13 | 44.9% | 58.1% |
| `schema v5 迁移`（20000） | 2000 ms | 575.33–657.06 | 597.70 | 32.9% | 32.9% |
| `FSRS computeTrain`（4000） | 20000 ms | 5446.64–5652.89 | 5529.90 | 28.3% | 29.8% |
| `keys() 写入已存在键后`（50000，自比值） | max(首次/10, 1 ms) | 0.06–0.11 | 0.08 | 2.7% | 9.5% |
| `IDB 单次评分写入`（5000 / 20000 / 50000，最小样本） | 1 ms | 最小样本 0.08 / 0.33–0.42 / 0.51–0.61（三次实测） | 0.09 / 0.40 / 0.60 | **61%**（50k） | 84 ms（不参与判定，见 3-B-2） |

上表 6 项中 4 项是**绝对毫秒中位数**门禁、1 项是**最小样本**门禁（`IDB 单次评分写入`，见 3-B-2）、1 项是**同进程自比值**门禁（`keys()` 写入已存在键后，见 3-B-1），都会随机器负载移动；比值类门禁（`merge 去重准备` ≤0.5×、SRS `grade`/`gradeMany` 的对标定比值、`keys()` 视图的同进程自比值）两侧同源漂移会抵消，本来就不需要多轮。另有 `keys()` 首次构建的 10 轮最小样本绝对门禁（21.53 / 29.30 ms，见 3-B-1），亦不在此表。

结论：保持单轮的那几项最差中位数都在 45% 以内（峰值样本最高 58.1%），余量足够，**保持单轮**；若全部改成三轮，预计只多花约 13 s（computeTrain 一项 11 s、schema 1.2 s、其余 <1 s），属于为不需要的精度买单，故不做。

`IDB 单次评分写入（50000）` 曾是唯一贴着上限的：中位 0.58 ms、最差一轮 0.83 ms（83% 预算），且随库存规模单调上升（0.10 / 0.42 / 0.58 ms 对应 5k / 20k / 50k）。实测三轮中位数后仍会随负载翻转（轮中位最高 **1.492 ms**、中位数最高 0.95 ms，见 3-B-2），故判定改为**最小样本 + 保持 1 ms**；若线上真触线，应查写入路径（尾段日志聚合与事务提交），而不是放宽阈值。

### 3-B. SRS 相对门禁（同轮标定比值）

**为什么改掉绝对毫秒阈值**
- 旧规则：`SRSStore.grade / gradeMany` 的 9 轮全样本 p50 ≤ **历史某次运行**的基线 ×1.05（0.0810 / 0.2604 ms）。
- 2026-11-03 同机复测：HEAD **0.0902 / 0.2787 ms**；同机跑旧代码 `e772e60` 为 **0.0882 / 0.2784 ms**，同样超限 → 机器漂移，不是本轮代码回退（本轮改动不进入 SRS 热路径）。
- 该口径有两个结构性问题：机器变慢 → **误报**；机器变快 → 阈值被动变宽 → **漏报真实回退**。因此不改阈值，改测量方法。

**方法**
- 每轮（共 21 轮）在被测样本批次**前后各跑一批标定工作**；标定工作与存储提交（`local-adapter` patch）同构：状态对象合并、200 条日志段拷贝、状态/尾段/首段/元数据 `JSON.stringify`、Map 缓存查表。标定只用标准 JS 常量与基元，不调用业务模块。
- 单轮判定量 `ratio = 本轮被测中位数 / 标定单位耗时`（前后两批取均值）；**门禁判定量取 21 轮比值的 p25**（不是轮中位数的中位数，理由见下）。
- 标定窗口与样本批次**同量级**：grade 每轮 5000 单位（≈200 ms）、gradeMany 每轮 2000 单位（≈80 ms）（`unitsPerSample` 5 / 10）。原标定仅 3–4 ms，与 80–200 ms 的样本批次处在不同 CPU 频率斜坡上，负载一起来两侧不同步。
- 门禁：`ratio(p25) ≤ 基线 × 容差`，**两项各自一个容差**（`node.<ver>.tolerance`），基线按 **Node 大版本** 存放于 `scripts/bench-baseline.json`。遇到未登记的大版本 **fail-closed**（直接判失败并提示「测量后补基线」），禁止拿别的引擎数字顶替。

**为什么把判定量从「轮中位数的中位数」改成「21 轮比值的 p25」（2026-11-12）**
- 旧口径（11 轮、标定 3–4 ms、判定量 = 11 轮比值中位数）连跑 20 次：grade **4.67–5.51**（p50 4.99），gradeMany **8.42–11.79**（p50 9.43，极差 **1.40×**），20 次里 **9 次红**。逐轮数据呈双峰（如 gradeMany 11.35/8.58/11.60/8.52…）：负载只会让个别轮变慢，中位数被周期性慢轮整体抬高，阈值 5.29 / 9.48 正好压在分布中部——这是当天反复误红的直接原因。
- 改法：轮数 11→21、标定窗口拉到与样本批次同量级、判定量取 **p25**。p25 取的是「这台机器上该路径的内在成本」，少数慢轮不再拖动判定值；同口径连跑 20 次，两项极差都收窄到 **1.10×**（见下表）。

> SRS 比值的 20 次分布、Node 24 对照、容差推导原始数值与负向注入结果见 [BENCH-DATA.md](BENCH-DATA.md)。

**这套容差能抓住多大的回归（以下三条是 A 之前的记录，阈值 5.07 / 8.99 已退役；现行判据见下方「2026-11-14 基线刷新」）**
- **≥20% 必然抓得住**：按本次最快观测态（grade 4.44、gradeMany 7.86）估算，+20% 后为 **5.33 / 9.43**，分别高于 5.07 / 8.99。
- **10% 取决于运行态**：按 p50 态（4.69 / 8.40）+10% 得 **5.16 / 9.24**，均越线；按最快态 +10% 得 **4.88 / 8.65**，抓不到。即 10% 级回退是否报警依赖当次机器状态，**保证可抓的下限是 20%**；若要求 10% 必抓，容差需压到约 1.04，会把 20 次观测里的 max 变成常态误红，故不采用（如实记录该折中）。
- 上两条对应 revlog 去重解析（A）**之前**的 7.86–8.40 区间；A 之后的可抓下限见下一条。

**2026-11-14 灵敏度变化（revlog 去重解析之后，如实记录折中）**
- 改动：`appendInternal` 的 `readSeg` 复用已读分段，去掉尾段/首段的重复解析；每批分段 `getFresh` **4.2 → 2.1 次**、分段解析字节 **44,314 → 22,157 B**。差分验证（HEAD vs 工作区，11 个场景含 3 条回滚路径）落盘、返回值、异常逐键一致。
- 同口径空载 6 轮 p25：**7.16 / 7.14 / 7.22 / 7.08 / 7.22 / 6.83**（中位 **7.15**，极差 1.06×，6/6 绿）；4 CPU 负载 2 轮：**6.65 / 7.33**（2/2 绿）。改动前同口径空载 7 轮为 7.67–9.33（中位 8.41），中位降幅 **15%**。
- 直接后果：判定值下降而 `8.99 = 8.40 × 1.07` 未动，**10% 级回退不再能判红**。`QF_BENCH_INJECT_SLOW=0.1` 两次实测 **7.71 / 7.28（绿）**，`0.3` 实测 **9.40（红）**；可抓下限由 20% 上移到 **≈26%**（`8.99 / 7.15 − 1 = 25.7%`）。
- 这是「用灵敏度换真实性能」的已知折中，**不是优化后更稳**：同一阈值下能拦住的最小退化变大了。要恢复 10% 灵敏度必须重建基线（判据变更，需单独授权）；阈值、采样口径、基线在本轮一律未动。

**2026-11-14 基线刷新（A 之后，属收紧）**
- **触发**：上一条的 ≈26% 下限不是标定负载的问题，而是「判定值降了、阈值没降」。旧基线 `gradeMany 8.40 / grade 4.69`（阈值 8.99 / 5.07）来自 revlog 去重解析（A）**之前**的代码，不是本轮代码的性能读数。
- **依据**：20 个独立进程 × 21 轮 × 200 / 1000 次的 p25 分布——`gradeMany` 6.454–7.704（中位 **7.417**，次间极差 1.039）、`grade` 3.089–3.468（中位 **3.288**，极差 1.055）。容差沿用原规则 `max / p50 × 1.03` 向上取两位：`gradeMany 7.704/7.417×1.03 = 1.070 → 1.08`，`grade 3.468/3.288×1.03 = 1.087 → 1.09`。新阈值 **7.42 × 1.08 = 8.01**、**3.29 × 1.09 = 3.58**。
- **验证**：干净态 20/20 绿（max 7.704 / 3.468，距阈值 3.8% / 3.1%）；10% 注入判红 **11/12 / 8/12**（**概率性结论**，单次运行不保证）；30% 注入判红 **6/6 / 6/6**，最小 8.96 / 4.59 分别高于阈值 11.9% / 28.2%（**确定性结论**）。原始分布与阈值试算见 [BENCH-DATA.md](BENCH-DATA.md) D-12、评估稿 `docs/rounds/2026-11-14/bench-calibration-eval.md`。
- **只改数字**：仍是 21 轮 × 1000 / 200 次、p25 判定量、同轮标定 V1；采样口径与标定负载均未动。实验表明换成同资源 JSON 标定（V2）会让次间极差变大、10% 判红率下降，故不采用。
- **不加兜底**：不引入「判红自动复跑」之类的机制——那会把误报转成漏报，并把单次结论变成重试次数问题。10% 按概率性口径记录，**30% 才是确定性承诺**。
- **已知盲区与补口（2026-11-14 定稿）**：以上口径仍是 `LS + Quota 未就绪`。生产形态（IDB + Quota ready）实测 `gradeMany` 比门禁口径慢 1.75×、冷读整库慢 9.7×，热度分布与结构性/可改成本见 [BENCH-DATA.md](BENCH-DATA.md) D-13。2026-11-14 已修掉其中两类可改成本（IDB 计费双次序列化、防抖 `set` 未预序列化，见 D-14）。**本轮新增第 64 项门禁**：生产形态 `gradeMany` 同轮标定比值（基线 13.071 × 1.06 = **13.86**），既有 63 条阈值一条未动；冷读明确不设门禁，理由见 **3-B-3**。

> Node 26 归因与证据留档见 [BENCH-DATA.md](BENCH-DATA.md)。

**为什么它能区分「机器漂移」与「代码回退」**
- CPU 频率/负载/GC 相位/JIT 状态会**同时**作用于被测路径与标定路径，在比值中同向抵消。
- 真实回退只发生在被测路径（分子），标定路径不变 → 比值单向上升；标定不引用业务实现，业务回退不会把标定值一起抬高。
- 容差由实测分布推导（1.08 / 1.09，2026-11-14 刷新，见上），覆盖 20 次观测上界再留 3% 余量：10% 级回退为概率性判红（11/12 / 8/12），30% 级回退 6/6 确定判红；再放宽会让 10–30% 级回退整体淹进噪声。

**测量前置条件（绝对毫秒不再可与旧口径比较）**
- **必须 `--expose-gc`**：每轮前 `global.gc()` 两次，消除堆相位差；无该参数时比值仍输出，但波动明显更大。
- 测量前把全局 revlog 灌到 `REVLOG_MAX`（20000），固定「尾段写 + 满段 FIFO 裁剪」稳态；否则测量窗口跨越 cap，p50 取决于越界轮次，不可复现。
- 标定拆 10 个小批取中位数，避免单批 GC 抬高单位耗时；每轮标定工作量已拉到与样本批次同量级（见「方法」），改动该量即作废两套基线。
- 因 revlog 预灌，新口径 p50（grade ≈0.16 ms、gradeMany ≈0.29 ms）**高于**旧口径（0.08 / 0.25 ms），二者不可直接比较；判定只看比值。

**适用边界（未验证项如实列出）**
- 已验证：Windows + Node v24.22.2（8 次）与 v26.13.0（20 次）、同机同负载量级、21 轮×1000 / 21 轮×200。
- **未验证**：跨 CPU 架构（x86/ARM）、容器限核/CI 共享核、swap 与磁盘 I/O 抖动、极端后台负载。接入新环境时应先跑 3 次记录比值，再决定是否新增该环境的基线（不是放宽容差）。
- 若某机器上「标定工作」与「业务 patch」对硬件特性的敏感度差异超过容差（7–9%），比值基线会整体平移，仍可能误报/漏报；这是相对法的固有边界。
- 覆盖不到：首次冷调用 JIT 编译（取中位数已排除预热阶段）、真实磁盘 I/O（bench 用内存适配器，不落盘）、GC 长暂停（p25 削弱但非消除）。

> 负向注入的命令与实测结果见 [BENCH-DATA.md](BENCH-DATA.md)。

### 3-B-1. keys() 视图门禁：首次构建 10 轮最小样本 + 命中自比值（2026-11-12 定稿）

**旧口径为什么失效**
- 旧规则：`keys() 首次构建（50000 · IDB）` 对「50000 次纯内存字符串物化」探针的同轮比值 ≤ 基线 × 1.06（Node 24 基线 1.38、Node 26 1.41）。
- 反证（2026-11-12）：`js/utils/storage.js` 自基线提交 `866f784` 到 HEAD **零改动**（`git diff 866f784..HEAD -- js/utils/storage.js` 为空），但
  - Node 24.22.2 连跑 6 次比值 **1.43 / 1.47 / 1.48 / 1.49 / 1.50 / 1.52**（中位 **1.485**），**6 次全部 > 阈值 1.46**；
  - 同一天 Node 26.13.0 的比值跌到 **1.07–1.16**（探针中位从 21.6 ms 漂到 26–28 ms），远低于基线 1.41。
- 归因：探针自身日间漂移 **30%**（Node 24 13–20 ms、Node 26 21–28 ms，同一天内也摆 1.3×），比值不是稳定量。这正是 CI `logic-tests (24, Asia/Shanghai)` 的 bench 步长期红、Node 26 偶发红，而本地六格全绿同源码的原因——**测量口径问题，不是业务回退**。

**新口径：首次构建 10 轮最小样本（绝对判据）+ 命中自比值**
- `keys() 首次构建（50000 · IDB）`：10 轮 × 20 样本，每轮前强制 GC，判定量 = **全局最小样本**，上限 = Node 大版本基线 × **1.35**：Node 24 基线 **15.95 → 21.53 ms**，Node 26 基线 **21.70 → 29.30 ms**；未知 Node 大版本 **fail-closed**。
- 为什么用最小值：负载/GC 只会让个别样本或某一轮变慢，**不会把最小值拉低**，所以最小值是稳定的绝对估计；中位数会被 GC 长尾抬高（同机 Node 24 单次运行中位 19.7–26.5 ms，摆 **34%**），40 ms 量级的中位数门禁挡不住正常漂移。而「命中 ≤ 首次/10」是自比值，构建整体变慢时按比例放宽，**结构上抓不到构建退化**，故只作附加判据。
- 附加：`keys() 写入已存在键后`（3 轮 × 20 样本）的**中位数** ≤ `max(首次构建中位数 / 10, 1 ms)`，抓「任何写入即失效 → 每次 `keys()` 重建」（自比值≈1）。
- 两版本分基：最小值口径下 Node 24 **15.95 ms**、Node 26 **21.70 ms**，差 **1.36×**，超出 1.35 容差能吸收的范围；同一基线会让一版长期误红或放水。

- 1.35 的来源：覆盖实测轮间极差（11–12%）与日间漂移，同时保留抓住 1.5× 退化的余量——Node 24 **1.5× = 23.93 > 21.53**，Node 26 **1.5× = 32.55 > 29.30**。Node 24 另一次无注入复跑最小 **14.83 ms**，说明基线取在最快态 7% 以内（偏保守一侧）。

> 10 轮最小值原始数值见 [BENCH-DATA.md](BENCH-DATA.md)。**抓得住 / 抓不住**
- **抓**：首次构建 ≥1.5× 退化（按实测基线）；「任何写入都让视图失效」（自比值≈1）；未知 Node 大版本（fail-closed）。
- **抓不住**：<1.35× 的退化（吸收日间漂移的代价）；整机变快 >12% 时，同一段代码的 1.5× 可能落到阈值下——此时绝对值仍在 20 ms 量级，用户可感知预算未被突破。
- **误红而非放水**：整机降频/限核使最小值升 >35% 时正常代码也会红，这是刻意保留的信号（先查环境，不放宽基线）。真实磁盘 I/O、冷 JIT 不在覆盖范围（内存 IDB 替身）。

> 1.5×/2× 与「写入即失效」的注入结果见 [BENCH-DATA.md](BENCH-DATA.md)。

**边界**
- 10 轮 × 20 样本、每轮前强制 GC 是口径的一部分；改动须重新实测并同步本节与 `scripts/bench-baseline.json`。换机器应重新建基线，不沿用本表数字。
- 最小值对「整机持续降频/限核」不免疫；本机正常态 15–22 ms，距阈值 21.53 / 29.30 ms 有 1.35× 余量。

### 3-B-2. IDB 单次评分写入：为什么不做同轮标定比值（改用最小样本）

**结论**：这一条**不做**比值化。探针测的是 CPU/内存吞吐，而写入抖动来自事务提交（双微任务完成）与 GC/事件循环调度，纯内存探针在结构上代表不了它；硬套只会把「随负载翻转」换成「随探针抖动翻转」。判定改为「5 轮 × 20 样本的全局最小样本 ≤ 1 ms」，上限仍是 **1 ms（未放宽）**。

**比值实测为何不成立（2026-11-12，Node 26.13.0，同一 HEAD）**
- 探针按 3-B-1 的思路构造：独立 `createMemoryIDB` 实例，每轮写 1 个状态键 + 200 条日志段，走完整 `put` 与事务完成（`recordBytes` 两次 `JSON.stringify`），不调用业务模块。
- 三轮比值：5000 档 **1.59 / 1.71 / 1.33**，20000 档 **8.26 / 7.05 / 6.92**，50000 档 **9.97 / 9.74 / 8.00**；轮间极差 **19–29%**，是 6% 容差的 3–5 倍。
- 探针自身耗时只有 0.06–0.10 ms（绝对抖动即 ±67%），与被测值同量级——分母的噪声不比分子小。
- 把探针加大到 30 样本 / 5 轮仍不稳（5000 / 20000 / 50000 = **1.33 / 6.92 / 8.00**）。
- 根因：`keys()` 的抖动是「50k 字符串物化」的 CPU 成本，同性质探针可以抵消（3-B-1 实测比值只摆 4%）；IDB 写入的抖动是事务排队与 GC 相位，探针越接近纯 CPU，越抵消不了。故判定**不适合比值化**，按任务约定不改实现为比值。

**替代判定：最小样本**
- 每档 5 轮 × 20 样本（共 100 样本），判定值取**全局最小样本**；每轮前强制 GC（与 3-B-1 同一复现性前提）。
- 为什么用最小值：写入是重尾分布（单样本 max 7.6–84.4 ms，来自 GC 长暂停与事务排队），1 ms 预算只可能被尾部击中；最小值代表「这台机器此刻单次写入的成本下限」，对突发负载尖峰免疫，同时不会掩盖真实回退（代码回退会抬高整个分布，含最小值）。
- 与比值法的区别如实写明：最小值对**整机持续降频/限核**仍会上升，这是刻意保留的信号（属机器容量问题，应查环境而非放宽 1 ms）；比值法能抵消这种平移，但在本条上换不来稳定性。

> IDB 写入的三次实测、「判定不随负载翻转」证据与负向注入命令见 [BENCH-DATA.md](BENCH-DATA.md)。

**边界**
- 最小样本对「整机持续降频/限核」不免疫（见上）；本机 50k 档实测地板 0.51–0.61 ms，距 1 ms 有 1.6–2 倍余量。
- 5 轮 × 20 样本、每轮前强制 GC 是口径的一部分，改动需重新实测并更新本节数字。
- 未覆盖：真实浏览器 IndexedDB 的磁盘事务语义（bench 用内存替身，口径声明见 `scripts/lib/idb-memory.mjs`）。

### 3-B-3. 生产形态门禁（`idbon` gradeMany，第 64 项）与冷读不设门禁（2026-11-14 定稿）

**为什么只加这一条、落在这里**
- D-13 证明生产形态（IDB + Quota ready）与门禁形态（LS + Quota 未就绪）不是同一形态，`gradeMany` 差 1.75×；D-14 修掉其中的可改成本后，差距仍在，**说明「形态差」本身没被门禁覆盖**。
- 选 `gradeMany` 而不是冷读/批量写：它是唯一「既有同轮标定口径、又直接跑在生产形态」的热路径；批量写与热读的抖动来源（事务排队、视图命中）与现有标定负载不同质，比值法在 **3-B-2** 已论证不成立。

**口径（与 3-B 完全同构，只换形态）**
- 21 轮 × 200 样本、每轮前置/后置各 10 批标定、判定量 = 21 个「轮中位数 / 标定单位耗时」比值的 **p25**、每轮前 `--expose-gc` 强制 GC。
- 形态改为 IDB 后端 + `Quota.refresh()` ready；夹具/预热（20 题批、revlog 灌满 `REVLOG_MAX`、60 轮预热）与 bench 内 `gradeMany` 一致。

**修完后的多进程分布（20 个独立进程 × 21 轮，Node 26.13.0，`--expose-gc`）**
- p25 比值：12.574 / 12.669 / 12.683 / 12.718 / 12.887 / 12.890 / 12.928 / 12.945 / 12.955 / 13.033 / 13.109 / 13.134 / 13.146 / 13.150 / 13.168 / 13.236 / 13.273 / 13.373 / 13.376 / 13.390。
- 中位 **13.07**、min 12.57、max **13.39**，极差 **1.065×**（max/p50 = **1.024**）。
- 容差按既有规则 `max / p50 × 1.03`：1.024 × 1.03 = 1.0552 → 向上取两位 **1.06**。
- **定稿阈值 13.86 = 13.071 × 1.06**，已写入 `scripts/bench-baseline.json` 的 `node["26"].idbonGradeMany`（容差 `tolerance.idbonGradeMany = 1.06`）；等价表述：**最坏值 13.390 之上留 3.5%**（13.390 × 1.035 = 13.8587 → 13.86）。
- 同探针的 LS 对照（8 进程）中位 7.77，`idbon / ls` ≈ **1.68×**，与 D-13 的 1.75× 同量级；bench 内夹具与探针**同夹具**（20 题合成批、revlog 灌满 `REVLOG_MAX`、60 轮预热），故 13.071 直接适用。落地首跑实测 **13.00（✓，余量 6.2%）**。
- **落点与顺序**：这一项放在全部既有测量之后。独立 harness 会增加堆占用，若前置会把 `IDB 单次评分写入（50000）` 的最小样本从 0.54 ms 抬到 1.21 ms（同机 A/B 实测）并挤红既有门禁；后置后该门禁恢复 0.66 ms 通过。

**判据性质：确定性只到 +20%，+10% 是概率性，不做自动复跑**
- **+20% 确定性判红**：三次注入 15.47 / 16.95 / 19.40，全部越线，最小余量 11.6%。
- **+10% 概率性判红**：三次注入 14.03 / 14.13 / 14.88，3/3 越线但**最小余量仅 1.2%**——单次运行不保证，不能当作承诺。
- **+5% 不承诺**：13.10 / 13.80 / 13.88，1/3 越线，落在噪声内。
- **不加自动复跑**：判红不重试。自动复跑会把误报转成漏报，并把结论变成「重试次数」问题；宁可保留一次可见的红，也不做静默放宽。
- **Node 版本跳过规则**：只有 Node 26 有该形态基线。Node 24/其它大版本打印 `✓ … Node <ver> 无该形态基线，跳过判定（仅 Node 26 判定）`，计入声明总数但不判定；**禁止拿别的引擎数字顶替**。这是当前唯一按版本跳过的门禁，已写进 §0「声明总数与本机执行数」。

**灵敏度（同一探针，注入只在 `scripts/` 侧忙等，不改产品代码）**
| 注入 | 三次 p25 | 对 13.86 | 结论 |
|---|---|---|---|
| +5% | 13.10 / 13.80 / 13.88 | 1/3 越线 | 抓不住（噪声内） |
| +10% | 14.03 / 14.13 / 14.88 | **3/3 越线**，最小余量 1.2% | 高概率、余量薄 |
| +20% | 15.47 / 16.95 / 19.40 | **3/3 越线**，最小余量 11.6% | 可作确定性承诺 |

- 与 3-B 主门禁的结论一致：**确定性承诺只到 +20%**；+10% 记作概率性，+5% 明确不承诺。
- 注入用「样本中位数 × 比例」定忙等时长，会轻微拉高 CPU 频率、低估注入幅度；因此它只证明「该幅度本容差下会判红」，不能反过来证明门禁更灵敏。

**冷读明确不设门禁（理由必须留在体系里）**
- Node 无原生 IndexedDB：`scripts/lib/idb-memory.mjs` 把结构化克隆实现为 JS 深拷贝、事务实现为微任务，**没有磁盘 I/O、没有 IPC、没有跨进程序列化**。所以 `idbon` 冷读 5.25 ms（D-13）是**下界**，不是生产成本。
- 用下界当门禁标准 = 给生产环境发一张虚假的安全感：浏览器里冷启动恰好发生在主线程最忙、磁盘最慢的时刻，真机读数只会更高；门槛按替身定，真实退化会被「替身跑得快」掩盖。
- 保留为**观测行**（D-13/D-14 存档），只做版本间趋势比对；真机冷启动要用 Performance API 在浏览器采，不在 Node 门禁体系里假装覆盖。
- 同理：批量写 540、热读 540 也只存档不设阈值（抖动来源与标定负载不同质，见 3-B-2）。

### 3-C. 哪些绝对阈值取三轮中位数、哪些保持单轮（取舍）

门禁的判定量都是中位数，但**单轮取样**在重尾分布上不稳：同一个 HEAD 连跑两次，`IDB 单次评分写入（50000）` 得到 1.13 ms 与 0.60 ms（阈值 1 ms），单样本 max 达 110 ms（GC 长尾）。因此按下面的分工处理，阈值一个都没动（`IDB 单次评分写入` 后来改为最小样本判定，见 **3-B-2**，本节其余分工不变）。

**取三轮**（`stableTimed(fn, n, 3)`；`per-hash` 判定取**全局最小样本**）：

- `per-hash 单次评分本地写`（20000 档，20 样本 × 3 轮；2026-11-12 起判定量从轮中位数改为最小样本：中位数被 GC 长尾污染，同机 Node 24 实测 0.18→0.38 ms 摆动 2.1×，阈值与相对判据不变）
- `keys() 写入已存在键后`（50000，20 样本 × 3 轮，判定取轮中位数；绝对耗时约 0.08–0.12 ms）

这些被测操作在 0.02–0.6 ms 量级，阈值是 1 ms 的绝对值，中位数离阈值近，长尾足以翻盘；三轮的额外成本可以忽略。

> `keys() 首次构建（50000）` 改为 **10 轮 × 20 样本的最小样本绝对门禁**（Node 大版本分基，见 **3-B-1**）；「写入已存在键后 vs 首次构建」的同进程自比值作附加判据。`Storage.keys()` 本身未改动。

**保持单轮**（`timed(fn, n)`，默认 10 或 5 样本）：

- `insertMany 落库`、`规模库 insertMany overwrite 全量重写`
- `schema v5 迁移`（1000 / 3000 / 20000）
- `FSRS 优化器 computeTrain`（4000 条 / 150 迭代，单次约 5.5 s）

> 10 次独立进程实测表见 [BENCH-DATA.md](BENCH-DATA.md)。

上述分工中 4 项是**绝对毫秒中位数**门禁、1 项是**最小样本**门禁（`IDB 单次评分写入`，见 3-B-2）、1 项是**同进程自比值**门禁（`keys()` 写入已存在键后，见 3-B-1），都会随机器负载移动；比值类门禁（`merge 去重准备` ≤0.5×、SRS `grade`/`gradeMany` 的对标定比值、`keys()` 视图的同进程自比值）两侧同源漂移会抵消，本来就不需要多轮。另有 `keys()` 首次构建的 10 轮最小样本绝对门禁（21.53 / 29.30 ms，见 3-B-1），亦不在此表。

结论：保持单轮的那几项最差中位数都在 45% 以内（峰值样本最高 58.1%），余量足够，**保持单轮**；若全部改成三轮，预计只多花约 13 s（computeTrain 一项 11 s、schema 1.2 s、其余 <1 s），属于为不需要的精度买单，故不做。

`IDB 单次评分写入（50000）` 曾是唯一贴着上限的：中位 0.58 ms、最差一轮 0.83 ms（83% 预算），且随库存规模单调上升（0.10 / 0.42 / 0.58 ms 对应 5k / 20k / 50k）。实测三轮中位数后仍会随负载翻转（轮中位最高 **1.492 ms**、中位数最高 0.95 ms，见 3-B-2），故判定改为**最小样本 + 保持 1 ms**；若线上真触线，应查写入路径（尾段日志聚合与事务提交），而不是放宽阈值。

### 3-D. 方向 F：50k IDB 热点夹具（`--hotspots`，2026-11-13）

**为什么加**：P2-3 原判定是「未发现收益」，但那只是**读码推断**——既有 bench 的 50k 档只覆盖迁移、单次写入与 keys 视图，
没有「50k 题 + 50k 复习状态 + 20k revlog 同库」下的读放大/全表扫描读数，无法证明某个热点到底有没有可测收益。
`--hotspots` 用同一内存 IDB 建这个最坏用例，逐点给出读数与独立红线；结论与「不改」的理由都有数据支撑。

**运行**

```bash
npm run bench:hotspots                                          # = node --expose-gc scripts/bench.mjs --hotspots --assert
node --expose-gc scripts/bench.mjs --hotspots                    # 只观测，不判定
node --expose-gc scripts/bench.mjs --hotspots --assert --snapshot # 绿灯也落快照到 .analysis/bench-snapshots/
QF_BENCH_HOTSPOT_SCALE=10 npm run bench:hotspots                 # 负向证明：判定值 ×10，热点门禁判红
```

**口径**

- 独立 `createMemoryIDB` + 独立 harness（与 12c/12d 同来源），不污染主 harness，也不进入默认 `npm run bench`。
- 夹具固定为 **50k 题（250 分片）+ 50k per-hash 复习状态 + 20k revlog（FIFO 上限）**，建库约 0.23–0.38 s。
- 热点行输出前缀 `  [H] ✓/✗`，**不匹配** `--assert` 自校验的 `^  [✓✗] `，因此 `GATE_TOTAL` 仍为 **63**；
  `--hotspots --assert` 下同样打印「门禁条数：64 项（与声明一致）」，既有 63 项的阈值与判据**一条未改**，新增的第 64 项只覆盖生产形态。
- 读路径 3 轮 × 5 样本取轮中位数；`commitReview` 写路径 5 轮 × 20 样本取**全局最小样本**（与 3-B-2 同口径）。
- 红线只拦「量级回归」：按实测基线 × 5–12（2 ms 级小绝对值项放宽到约 50×），不追求跨机器严格；换机器应重测并同步本表。
- 红灯取证沿用 `.analysis/bench-failures/`，新增 `hotspots` 段（逐项 `measuredMs/budgetMs/pass`）、`flags`
  （`assert/hotspots/snapshot`）与 `QF_BENCH_HOTSPOT_SCALE`；绿灯默认不落文件，`--snapshot` 时写 `.analysis/bench-snapshots/`。
- 口径声明：Node 内存 IDB 替身，**不是浏览器真实 IndexedDB**；绝对耗时只可与同机同口径比较，真实事务/磁盘语义未验证。

| `SRSStore.writeMap` | 512–538 ms | 6000 ms | 不改 | 与 `reviews.save` 同实现，多一次 `confirmPersisted` |
| `removeMany` 全库扫描 | 2.0–2.4 ms | 100 ms | 不改 | 按 meta 分片遍历（250 片），不是逐题全库反序列化 |
| `Storage.usageBytes` 全量 | 51–53 ms | 500 ms | 不改 | 全量扫描是 API 语义；渲染路径已改走 Quota 快照（C009），不再每帧调用 |
| `isBankHydrated` 未水合库 | 1.3–1.5 ms | 100 ms | 不改 | 扫 50k 键成本可忽略；加缓存会引入失效语义 |
| `revlog.list` 全量（20k） | 0.9–1.2 ms | 200 ms | 不改 | 返回缓存数组；app 侧 `reviewLogFor` 按库缓存，评分后失效 |
| `ReviewQueue.dailyFromLog`（20k） | 2.4 → 1.9 ms | 50 ms | **改** | 两遍遍历合并为单遍；同进程 A/B 两次比值 **0.524 / 0.797**（−20%～−48%），结果逐项一致 |
| `ReviewQueue.build`（50k） | 11.4–13.5 ms | 200 ms | 不改 | 单遍分组 + 两次 sort 已是最小必要 |
| `SRSStore.stats` | 84–94 ms | 700 ms | 不改 | 成本即 `readMap`，同上 |
| `Statistics.reviewStats`（20k） | 0.66–0.84 ms | 20 ms | 不改 | 单遍聚合 Map，已是最小必要 |

**本轮改了什么**：`js/modules/review-queue.js` 的 `dailyFromLog` 由「两遍遍历 + newHashes 中间表」改为「单遍收集
firstSeen + 今日条数」，`reviewsDone = 今日全部条数 − 今日新卡条数`（新卡的日志必然都在今日，等价性已由单测与
同进程 A/B 结果一致双重验证）。两次同进程 A/B 为 **2.42 → 1.93 ms（0.797）** 与 **3.36 → 1.76 ms（0.524）**，
保守口径收益 **≥20%**，绝对收益约 **0.5–1.6 ms/次**（20k 日志）；不改变返回值结构与任何口径。

**如实记录的限制**：
- 其它热点全部「不改」——不是没测，而是测得收益不足以支撑改动，或改动会改语义（见上表「依据」）；
  `readMap`/`stats`/`usageBytes`/`save` 的整表成本本身是接口语义，压平需要改调用面或缓存策略，超出「不改语义」边界。
- 本夹具只覆盖内存 IDB 替身；真实浏览器 IndexedDB 的大库读放大（尤其 `readMap` 的逐键读）**未实测**。
- 各次运行整体漂移可达约 20%（同机负载），因此 `dailyFromLog` 的收益只用**同进程 A/B** 归因，跨轮绝对耗时只作参考。

### 3.1 开发子任务计时埋点（`scripts/task-timer.mjs`）

`bench.mjs` 量的是**代码热路径耗时**；开发流程要求的「每个子任务耗时 / subtask 明细表」由 `task-timer.mjs` 量**开发墙钟**（谁在什么时间开始/结束）：

```bash
node scripts/task-timer.mjs reset                       # 开新会话前清空
node scripts/task-timer.mjs start s4-timer "计时埋点 CLI + 文档"
node scripts/task-timer.mjs end   s4-timer              # 结算耗时并打印
node scripts/task-timer.mjs report                      # 明细表 + 已完成合计 + 会话墙钟
```

- 记录落 `<工程根>/.qforge-timings.json`（已 gitignore）：**仅本地开发用，不入库、不参与构建、不被应用运行时读取**。
- 用途：任务收尾报告的「subtask 时间明细表」以**实测**为准（对应红线「没有数据就是没做」），不凭记忆估算。
- 数据误差声明：测量点是「两次 CLI 调用之间」，包含开发者在该子任务上的全部时间（含思考/工具往返），非纯编码时长。

### 3.2 按需包体积上限（`scripts/check-bundle-size.mjs`，防漂移门禁）

按需包不进首屏口径，只会单向增长；没有上限时任何一次「顺手加一个文件」都不会被拦住。
2026-11-14 按需包从 117.1 KB 涨到 122.4 KB gzip 后，把当时的构成落成可执行上限：

| 包 | 上限（KB gzip） | 当时实测 | 余量 | 文件数 |
|---|---|---|---|---|
| `backup` | 30 | 28.7 | 1.3 | 3 |
| `import` | 62 | 60.3 | 1.7 | 19 |
| `editor` | 27 | 25.6 | 1.4 | 5 |
| `export` | 29 | 27.6 | 1.4 | 7 |
| 全包去重 | 125 | 122.4 | 2.6 | 28 |

- **口径**：与首屏体积统计一致——逐文件 `zlib.gzipSync(buf, { level: 9 })`，KB = bytes/1024（报告 1 位小数），
  包内按 URL 去重求和，全包去重 = 四包文件并集（`adapters-normalize` / `dsv` 等跨包文件只算一次）。
  包清单不复制，直接从 `js/modules/loader.js` 的 `BUNDLES` 读取。
- **判定**：用字节精确比较（上限 × 1024），避免四舍五入把「刚好超」显示成相等；超限时输出包名与超出量。
  新增/删除按需包而未同步上限表同样判红。
- **这是防漂移的线，不是优化目标**：拆分/重构导致包变大时，先解释净增量；确需提高上限，
  必须在同一次改动里给出构成变化，不能只调数字。命令：`node scripts/check-bundle-size.mjs`
  （已接入 `verify:fast`，也可 `npm run check:bundles`）。
- **负向样本已验证**（两次真实输出留存于本地 `2026-11-14/bundle-gates/`）：向 `import`/`editor` 共用的
  `js/importers/adapters-normalize.js` 追加 24 KB 随机内容后，门禁判红并报
  `import 85.7 > 62.0（超 23.7）`、`editor 51.0 > 27.0（超 24.0）`、`全包去重 147.8 > 125.0（超 22.8）`，退出码 1；
  还原文件（SHA256 与追加前一致）后回到 60.3 / 25.6 / 122.4，门禁通过。

> 启动分阶段水合验收（Phase 0 批次2）的协议、数据与判定见 [BENCH-DATA.md](BENCH-DATA.md)。

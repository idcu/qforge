**分级口径（P0/P1/P2）为什么这么定**：P0 = **无需极端前提**即可造成用户数据丢失或不可恢复；P1 = 特定并发/失败路径下丢数据或用户可见结果错误；P2 = 长期维护成本、一致性与性能问题。按此口径共 P0 6 项 / P1 17 项 / P2 13 项。

> **看似矛盾的两句话**：审计总体判断「无发布级阻塞缺陷」，开发计划却把 P0 列为「发版阻塞项」。两者评的不是同一件事——前者评架构方向是否要推倒重来，后者评**是否允许在 P0 未修完时继续发布**。计划选择了更严格的发布门槛，这是当时的明确取舍。

## 2. 为什么先修 P0

P0 的判定不靠“理论上可能”，必须同时满足：

1. 有可复现路径（能写成失败注入用例）；
2. 有代码级证据（文件与行号，可在底稿中复算）；
3. 影响是数据丢失/不可恢复，而不只是显示错误。

当时的 6 条 P0 与修法方向：

| ID | 问题 | 修法方向 |
|---|---|---|
| P0-1 | 迁移先提交版本号、后刷盘 | 写入「迁移中」标记 + 启动自愈（见 D1） |
| P0-2 | 恢复 replace 失败后已删键不恢复 | 失败时按内存快照全量回写 |
| P0-3 | 跨标签 append 读-改-写丢题 | 比较-重试 + 题目集合合并 |
| P0-4 | insertMany 失败不回退去重索引 | 去重索引两阶段生效，失败回退 |
| P0-5 | 评分“先置位后落盘” | 写盘成功后再置位（后来按 at-least-once 取舍，见 [ARCHITECTURE §8](../ARCHITECTURE.md)） |
| P0-6 | IDB 模式下配额恒放行 | 有限上限 + 写入前预检 |

**数据修复的附加规则**：触碰迁移/备份的修复必须同时提供“旧数据向前修复”路径，不能只靠代码回滚。**翻案条件**：只有能证明该路径已被数据格式或存储原语消除（例如出现可用的原子 CAS），才允许从清单移除，并补一条能复现原问题的断言。

## 3. 决策与理由

### D1 迁移修复策略：选 B（迁移中标记 + 启动自愈）

- **为什么**：只调整写入顺序（A）无法覆盖“进程在两次写入之间被杀”；B 多一个引导键，但能在下次启动检出并重跑。
- **成立条件**：启动流程有唯一的迁移入口，且标记写入与刷盘顺序可被测试注入验证。
- **翻案条件**：存储层提供跨键原子事务，或迁移改为可重入的幂等算法且不再需要标记。

### D2 正确率口径：判分侧唯一函数

- **决策**：`accuracy = round((correct + partial) / (correct + partial + wrong) * 100)`；半对计入分子，待自评（pending）不计入分母。统计视图、成绩页、导出报表全部调用同一函数。
- **为什么**：旧实现有三套口径（半对处理不同），同一场考试能出现三个百分比。审计曾建议 `(correct + 0.5 × partial) / total`，**未采纳**：待自评不是“答错”，放进分母会让未完成的自评把正确率压低。
- **成立条件**：判分结果能区分 correct / partial / wrong / pending 四态。
- **翻案条件**：产品明确要求“得分率”而非“已判正确率”时，只改这一处函数，并同步历史归一与导出字段；不要在视图里各写一份。

### D3 FSRS 毕业：保持实现，只改文档

- **决策**：`mode='new'` 用毕业评分重新初始化 S/D，`mode='review'` 沿用；不改调度实现，只把 `docs/SRS.md` 的歧义措辞改精确。
- **为什么**：原审计把“文档与实现不符”当作缺陷，复核发现文档并未明确“毕业保留学习期 S/D”，属于歧义而非实现错误；改实现会改变新卡间隔分布。
- **翻案条件**：若产品决定毕业保留学习期 S/D，必须同时改实现、迁移已产生的调度、更新文档与训练口径，并给出对照读数。

### D4 WebDAV 的 http：保留但强提示（B）

- **决策**：不默认拒绝 `http:`，但在同步设置里显示明文传输风险提示。
- **为什么**：默认拒绝会打断自建 HTTP 服务的用户；风险提示能让用户知情。
- **翻案条件**：若把安全基线提高到“默认拒绝明文”，需要先提供迁移指引（本机/内网例外），否则属于破坏性变更。

### D5 不引入 ESLint

- **决策**：保持零 devDependencies，用仓库内零依赖脚本 `scripts/check-async-hygiene.mjs` 守 `no-empty` / `no-floating-promises` 两类问题，历史存量走**有到期日**的基线。
- **为什么**：为两条规则引入依赖树与锁文件，与“静态文件即产物、零运行时依赖”的形态冲突。
- **翻案条件**：允许 devDependencies 且 CI 能稳定安装时再评估；替换前必须保证新判据能抓住现有基线里的负例。

### D6 local / api 语义：按切片逐步对齐，不一次性统一

- **决策**：不把 `reviews/revlog/weights` 全部改 async 来强行对等；按模块分批补 `await` 与契约测试，逐项对齐（例如 2026-11-13 这批把本地 `questions.update` 的 `baseUpdatedAt` 冲突对齐为 api 同形的 409）。
- **为什么**：一次性改签名会波及大量未 `await` 的调用点，属于超切片规模。
- **翻案条件**：需要“切换后端零行为差异”时，先补 local 与 api 跑同一组用例的双向契约测试，再改实现；不允许只改文档假装对等。

### 版本节奏：只发布 1.0.2，v1.1.0 / v1.2.0 作废

- **决策**：阶段 1、2A、2B、2C、阶段 3 的交付全部并入 v1.0.2；应用版本只在真正对外发布时 +1，CACHE 每批独立 +1（回滚也用更大的新号）。
- **为什么**：各批在同一轮内连续完成并一起通过总闸；`check-release` 日常模式只要求版本不低于台账、CACHE 不回退。
- **翻案条件**：下一次对外发布按 semver 前进（起点 1.0.3）；不要把作废的 v1.1.0 / v1.2.0 当欠账。

## 4. 被新判据替代的旧标准

| 领域 | 旧口径 | 新口径 | 替代原因 |
|---|---|---|---|
| 性能门禁条数 | 66 项 | **63 项** | 三档 IDB 写入被 `BUDGETS` 表与独立判定块各判一次，同一断言打印两行；删重复后实跑 63。三方对账：`GATE_TOTAL` = 实跑行数 = 基线 = 文档 |
| UI 拆分首屏预算 | 每批增量 ≤ 0.5 KB | **全部拆完累计 ≤ 3 KB** | 逐批 0.5 KB 会误杀“单批收益大但总量可控”的拆分；累计口径才对应真实预算（见 [docs/README §3.1](../README.md)） |
| 首屏体积 | 资源个数 / 总字节（94 资源 / 1,098 KB） | **固定文件集合逐文件 `gzip -9` 合计** | 资源数随按需包拆分变化，不是稳定判据；固定文件集才能复算。历史读数并列保留在 [BENCH-DATA](../BENCH-DATA.md) |
| 断言总数 | 6,025（审计开工） | 6,208（阶段 2 收口）→ **6,245**（2026-11-13 缺陷复核） | 断言只增不减；它是读数不是阈值，必须由 `docs-check --write` 刷新基线与文档同步 |
| 索引/视图性能 | 绝对毫秒阈值 | **同轮标定比值 1.5×**，基线按 Node 大版本 ×1.35 分基 | 绝对毫秒随机器与 Node 版本漂移；比值在同一进程内标定，保留抓 1.5× 退化的能力（见 [BENCH §3-B](../BENCH.md)） |
| IDB 单次写入 | 中位数 / 带宽比值 | **10 轮最小样本 ≤ 1 ms** | 写入是重尾分布，中位会被负载翻转；最小值代表机器此刻成本下限，且代码回退会抬高整个分布 |
| 10k 重复导入 | 整次热/冷 ≤ 0.50 | **去重准备新/旧比值 ≤ 0.50**，整次保留为诊断 | 两臂耗时主要在逐题 `contentHash`，与去重索引无关；旧判据测不到被移除的 `readAll`+Set 工作 |
| 正确率 | 三套视图各自计算 | **判分侧唯一函数**（见 D2） | 同一场考试出现三个百分比 |
| reviewMeta 布局 | v3 全量 keys 清单 | **v4 紧凑标记（7 B）** | 每次新增 hash 都重写整表，1 万条新 hash 可累计数 MB |
| 文档数字校验 | 历史 live 实跑 | **`verify` 用 `--static` 基线对账**（`--write` 时才实跑） | 总闸速度；代价是基线可能陈旧——见 §6 |

## 5. 明确不做

- **不引入打包器 / 框架 / TypeScript**：当前形态的部署与调试优势与 2.3 万行规模匹配，改造收益低于风险。
- **不重写导入解析栈**：已有上限与坏样本用例，补 fuzz 即可。
- **不硬塞超切片事项**：`P1-1d` 同步/异步统一、`DB.Cache` 跨标签失效、ESLint、`ui-renderer` 拆分、发布自动化都要求拆卡或单独立项；不要在修一个小缺陷时顺手改签名。
- **ngm 适配层替换**：已单独否决，重启条件见 [ngm-no-go.md](ngm-no-go.md)。

| 风险 | 现状 | 翻案/消除条件 |
|---|---|---|
| 跨标签与并发写窗口 | 已做 fresh 读 + 回读校验 + 重试，但仍非原子 | 存储层提供 CAS/事务，或改为单写者模型 |

| 空 catch / 无 lint | 由 `check-async-hygiene` 与有到期日基线守，不是零 | 引入 ESLint 或把所有豁免清零 |
| `docs-check --static` 盲区 | 文档数字取自基线，基线不刷新就可能“文档绿、实测漂移” | 改完测试/门禁后跑 `node scripts/docs-check.mjs --write`；发版前用 live 模式复核 |
